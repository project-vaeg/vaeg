# NEON RELAY 4 P0-0 reuse inventory

Status: P0-0 inventory only. No NEON4 source or VA backend was generated by
this step. The table records reusable interfaces, not a claim that a 4bpp
implementation is valid for the NEON4 256-colour target.

## 1. Evidence inspected

| Asset | Relevant evidence |
|---|---|
| `demos/neon3` | `src/neon_counter.asm`, `build.sh`, the VA debug scripts, and `README.md` |
| `demos/sgp-pseudo-sprite` | `sgp_sprite.asm`, final build scripts, and `README.md` |
| NEON3 VA design/contract | `docs/port/neon3_va_video_contract.md`, `docs/port/neon3_va_design.md` |

NEON3 is a monolithic 16-colour G0/4bpp harness rather than a standalone
backend library. The pseudo-sprite demo is a 320x200 G0/G1/4bpp implementation
with a complete SGP BITBLT path. Both are useful references, but neither
contains the NEON4 256-colour RGB332/direct-pixel path.

## 3. What can be reused without re-proving the whole interface

The following are implementation patterns already present in both or one of the
references and are suitable starting points for later milestones:

1. VA BIOS entry/leave transaction shape, descriptor-list placement, palette
   call ordering, and explicit return-code checks from `neon_va_enter` and
   `initialize_video`.
2. TSP `0142h` bit-6 low-to-high VBLANK polling, with a bounded timeout.
3. A hidden-page state machine: render to the non-displayed page, wait for SGP
   idle, wait for VBLANK, write both DSA words, then exchange page state.
4. Main-RAM segment-to-physical-address conversion and the SGP command-table
   submission sequence at ports `0500h`, `0502h`, `0504h`, and `0506h`.
5. The basic `SET_WORK` / `SET_COLOR` / `CLS` / `LINE` / `END` emitters from
   NEON3 and the `SET_SOURCE` / `SET_DEST` / `BITBLT` descriptor construction
   from the pseudo-sprite demo.

These are reuse candidates, not proof of a NEON4 256-colour contract. P1 must
resolve RGB332 bit placement, 8bpp word/pixel ordering, FB0 page capacity,
descriptor fields, and BITBLT source/destination semantics before code is
generated.

## 4. New work required for NEON4

P0-0 identifies the following as genuinely new or not available in the
references:

- 256-colour packed mode setup for both 320x200 and 640x200;
- RGB332 direct pixel encoding and 8bpp byte/pixel ordering;
- two 8bpp FB0 pages, including page stride and display-start coupling;
- one source tree with a build-time X mapping (`X >>= 1` only for 320x200);
- exact 8bpp span endpoint handling and a CPU verification renderer, if the
  P0-4 comparison requirement is retained;
- 8bpp `BITBLT` source/destination descriptors and VRAM-to-VRAM operation for
  RASTER TRANSFER;
- NEON4 scene-specific command-count accounting and frame-skip scheduling;
- OPNA/YM2608 integration and 32-bar music progression;
- a NEON4 headless capture/verification harness built around the existing VAEG
  debug-script mechanism.

## 5. P0-0 conclusion

Reuse is substantial for VA BIOS lifecycle, VBLANK, page-state management, SGP
list submission, basic `CLS`/`LINE`, and `BITBLT` descriptor construction. It is
not sufficient to claim that NEON4's target mode is already implemented: both
references are 16-colour/4bpp, neither contains a CPU reference backend or an
OPNA player, and neither proves the required 8bpp FB0/descriptor contract.
The NEON4 scene colour path is direct RGB332 generation, not frame palette
animation.

P0-0 is complete. No code was changed. The next authorized step is P0-1 or P1
according to the milestone gate. The RGB332 choice is a NEON4 design decision;
the inventory does not infer the VA 8bpp bit order or descriptor values.
